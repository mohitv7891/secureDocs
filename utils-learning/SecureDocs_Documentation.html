1. Project Overview

SecureDocs is an end-to-end encrypted document sharing platform designed to allow IIITA users to exchange confidential files with absolute cryptographic guarantees. Unlike conventional systems that encrypt files at rest, SecureDocs encrypts documents before they reach the server, using the recipient's email address as the encryption key through Identity-Based Encryption (IBE).

Core Security Guarantees

  • The Data Server stores only ciphertext — it never holds decryption keys.
  • The KDC holds only encrypted private keys — it never sees file content.
  • Private keys are encrypted with the user's password before being emailed.
  • Digital signatures guarantee that the recipient can verify the sender's identity.
  • All cryptographic operations (sign, encrypt, decrypt, verify) run in the browser via WebAssembly.

1.1 Problem Statement

Traditional secure file sharing relies on a single trusted server holding both encrypted files and the keys — creating a single point of compromise. SecureDocs solves this by architecturally separating the KDC and Data Server, and by performing all crypto client-side so no plaintext ever travels over the network.

1.2 Key Innovations

  • Identity-Based Encryption (BLS/Boneh-Franklin): Any user's email is inherently their public key — no certificate exchange required.
  • Client-Side WebAssembly Crypto: The entire IBE/signature pipeline (C + PBC + OpenSSL) compiled to WASM runs directly in the browser.
  • Decoupled Architecture: Two independent MongoDB clusters and two independent Node.js servers ensure that compromising either one yields nothing useful.
  • Password-Encrypted Private Keys: Keys are wrapped with AES-256-GCM (PBKDF2-derived key) so the email carrying the key is useless without the password.

4. Cryptographic Design

4.1 Identity-Based Encryption (IBE) — Boneh-Franklin / BLS

IBE eliminates the need for public key certificates. A user's email address is their public key. The KDC's master secret key is used to derive per-user private keys. The scheme used is the Boneh-Franklin IBE constructed over Type-A bilinear pairings (via the PBC library).

IBE Mathematical Summary

PhaseOperationResult
Setup (run once) Pick generator g ∈ G₁, random msk ∈ Zp Public params: (g, Ppub = gmsk)
KeyGen (per user) did = H(id)msk where H: {0,1}* → G₁ User's private key did
Encrypt Pick random r ∈ Zp; compute U = gr, V = m ⊕ KDF(ê(H(id), Ppub)r) Ciphertext (U, V)
Decrypt m = V ⊕ KDF(ê(did, U)) Plaintext m

KDF is a SHA-256-based key derivation on the pairing output, producing a 32-byte XOR mask (stream cipher substitute).

4.2 BLS Digital Signatures

Before encryption, the sender signs the raw file bytes using their own IBE private key as a BLS signing key. The signature is concatenated with the file before encryption, so the recipient can verify sender identity after decryption.

BLS Signature Scheme

OperationFormula
Signσ = dsenderH(m) where H: msg → Zp
VerifyCheck ê(σ, g) == ê(H(idsender)msk, gH(m))

The sender ID (email) and public params are sufficient for the verifier; no additional public key exchange is needed.

4.3 AES-256-GCM — Private Key Protection

Raw IBE private keys are never transmitted in plaintext. Before being emailed, the KDC wraps each key with AES-256-GCM using a key derived from the user's password:

Encrypt raw private key with AES-256-GCM encryptAES(rawKeyBuffer, derivedKey) // random 12-byte IV, 16-byte auth tag // 3. Package for email attachment // Format: [Salt(16)] [AuthTag(16)] [IV(12)] [EncryptedKey] packageEncryptedData(salt, iv, encryptedData, authTag)

4.4 In-Browser Decryption (Web Crypto API)

The client-side cryptoUtils.js mirrors the KDC's crypto exactly using the browser's native SubtleCrypto API — no crypto library is shipped to the client:

// client/src/utils/cryptoUtils.js const baseKey = await subtle.importKey("raw", passwordBytes, "PBKDF2", ...); const aesKey = await subtle.deriveKey({ name: "PBKDF2", salt, iterations: 100000, hash: "SHA-512" }, ...); const rawKey = await subtle.decrypt({ name: "AES-GCM", iv, tagLength: 128 }, aesKey, ciphertext‖authTag);

5.1 Build Pipeline

    ↓ emcc (Emscripten)
+ Linked Libraries: libpbc.a (bilinear pairings) + libssl.a / libcrypto.a (OpenSSL 3.0.13)

5.2 Exported WASM Functions

C FunctionJS ExportDescription
wasm_sign_buffer() Module._wasm_sign_buffer Sign a message buffer with the IBE private key. Returns compressed G₁ signature bytes.
wasm_encrypt_buffer() Module._wasm_encrypt_buffer IBE-encrypt (msg ∥ sig) for a recipient email. Returns compressed U ∥ V ciphertext.
wasm_decrypt_buffer() Module._wasm_decrypt_buffer IBE-decrypt ciphertext using the caller's private key. Returns plaintext (msg ∥ sig).
wasm_verify_buffer() Module._wasm_verify_buffer BLS-verify the signature against the sender's identity and the recovered message.
wasm_free_buffer() Module._wasm_free_buffer Free C-allocated output buffers (caller must invoke after consuming results).

5.3 Emscripten Glue File (crypto_module.js)

The glue file is an Emscripten-generated JavaScript wrapper (~3000 lines, minified) that:

  • Detects the runtime environment (browser, Worker, Node.js) and configures file loading accordingly.
  • Implements MEMFS — a complete in-memory virtual filesystem so the C code can call POSIX file I/O (fopen, fread, etc.) on files preloaded from the browser.
  • Instantiates the .wasm binary via WebAssembly.instantiateStreaming() (with ArrayBuffer fallback).
  • Exposes Module.HEAPU8, HEAP32, etc. for reading/writing the WASM linear memory from JavaScript.
  • Provides ccall / cwrap helpers for C-to-JS type conversion (strings → UTF-8 pointers, arrays → heap pointers).
  • Exports the async factory: createCryptoModule() — resolves with the fully initialized Module once WASM is ready.
⚠️
Memory Management All buffers returned by wasm_sign_buffer, wasm_encrypt_buffer, and wasm_decrypt_buffer are malloc-allocated in C. JavaScript must call wasm_free_buffer(ptr, len) after copying the result into a JS Uint8Array, or WASM heap memory will leak.

5.4 Virtual Filesystem Initialization

// Dashboard.jsx — on component mount const Module = await createCryptoModule(); // instantiate WASM const paramsBuffer = await fetch('/a.param') // fetch pairing params .then(r => r.arrayBuffer()); Module.FS_createDataFile('/', 'a.param', // write to MEMFS new Uint8Array(paramsBuffer), true, false); // C code running inside WASM can now call: // FILE *fp = fopen("/a.param", "rb"); // works!

6. User Registration Flow

ℹ️
Registration is a two-step process: OTP verification first, then key generation and distribution. Only @iiita.ac.in email addresses are accepted.
1
User submits registration form (name, email, password) → Client POSTs to KDC /api/auth/register/initiate.
2
KDC validates email domain (@iiita.ac.in), hashes password with bcrypt (10 rounds), generates a 6-digit OTP (crypto.randomInt), and saves a PendingRegistration document (TTL: 10 minutes). Temporarily stores plaintext password for key derivation after OTP verification.
3
KDC emails OTP to the user's IIITA address via Nodemailer (SMTP/SSL on port 465).
4
User submits OTP → Client POSTs to KDC /api/auth/register/verify.
5
KDC verifies OTP + expiry. On success, it calls executeKeygen(email) which spawns the native C binary:
$ ./keygen user@iiita.ac.in
The binary reads a.param + master_secret_key.dat from opt/crypto-native/ and writes user@iiita.ac.in_private_key.dat (raw binary G₁ element).
6
KDC reads key file into memory, then immediately deletes the temp file from disk. The raw key never persists on the KDC filesystem.
7
KDC encrypts the private key with AES-256-GCM:
  • Generates a random 16-byte salt, stores it in the User document as kdfSalt.
  • Derives AES key: PBKDF2(password, salt, 100000, 32, sha512).
  • Encrypts: AES-256-GCM(rawKey, aesKey, randomIV).
  • Packages: [Salt(16)][AuthTag(16)][IV(12)][EncryptedKey].
8
KDC saves User to MongoDB (Cluster A): stores email, bcrypt hash, kdfSalt. The encrypted key package is not stored — only emailed.
9
KDC emails the encrypted key package as a binary attachment to the user. The email subject reads: "Your SecureDocs Private Key".
10
User downloads the attachment, loads it in the KeyLoader component, enters their password → the browser decrypts it using SubtleCrypto (PBKDF2 + AES-GCM) and holds the raw private key buffer in memory (AuthContext state) for the session.

7. File Upload (Encrypt & Sign) Flow

🔐
All cryptographic operations happen entirely in the browser using the WASM module. The Data Server receives only ciphertext and never sees the plaintext file.

Prerequisites (in browser memory)

  • WASM Module loaded + a.param written to MEMFS
  • public_params.dat fetched (contains compressed g ∥ Ppub)
  • Sender's decrypted private key buffer (from KeyLoader + SubtleCrypto)
  • Valid JWT token (from KDC login)
1
User selects a file and enters recipient email. FileUpload.jsx reads the file as an ArrayBuffer → Uint8Array.
2
WASM Sign: Allocate private key buffer on WASM heap. Call Module._wasm_sign_buffer(privKeyPtr, privKeyLen, msgPtr, msgLen, outLenPtr). Returns a pointer to the compressed G₁ signature bytes (σ).
3
WASM Encrypt: Construct plaintext as message ∥ signature. Call Module._wasm_encrypt_buffer(pubParamsPtr, pubParamsLen, recipientEmail, msgPtr, msgLen, sigPtr, sigLen, outULenPtr, outTotalLenPtr). Returns a pointer to compressed_U ∥ V.
4
Copy ciphertext from WASM heap into a JS Uint8Array, then call wasm_free_buffer(ptr) to release C-allocated memory.
5
POST to Data Server: Build a FormData object with the ciphertext blob (filename: original.ext.<recipient_email>.enc) and recipientId. Attach JWT in Authorization: Bearer <token> header.
6
Data Server stores ciphertext to MongoDB Cluster B as a Document with senderId (email), recipientId (email), originalFileName, and encryptedData (binary Buffer).

8. File Download (Decrypt & Verify) Flow

1
User opens Dashboard. FileList.jsx calls GET /api/files/received (JWT required). Data Server queries MongoDB B for documents where recipientId == req.user.email. Returns metadata list (no encrypted data included).
2
User clicks Download. Client calls GET /api/files/download/:id (JWT required). Server verifies the requesting user's email matches recipientId on the document, then streams the binary encryptedData buffer back.
3
WASM Decrypt: Allocate buffers. Extract U-length from the ciphertext header (stored during upload). Call Module._wasm_decrypt_buffer(privKeyPtr, privKeyLen, uPtr, uLen, vPtr, vLen, outLenPtr). Returns plaintext = message ∥ signature.
4
Split plaintext. Based on the stored original file length (or a delimiter/header), split the decrypted buffer into messageBytes and signatureBytes.
5
WASM Verify: Call Module._wasm_verify_buffer(pubParamsPtr, senderEmail, msgPtr, msgLen, sigPtr, sigLen). Returns 1 (valid) or 0 (invalid). If invalid, the user is warned about possible tampering.
6
Present file to user. Create a Blob from messageBytes, trigger a download with the original filename. Show verification badge ✓ or ✗.

✅
End-to-End Security Chain The Data Server cannot decrypt anything (it has no private keys). If a third party intercepts the email, the encrypted key attachment is useless without the user's password. Even the KDC cannot read the files (separate DB, no ciphertexts).

9. Security Architecture

9.1 Threat Model & Mitigations

ThreatMitigation
Data Server compromise Only ciphertext stored. No keys on this server. Attacker gets unusable blobs.
KDC database compromise Keys are AES-GCM encrypted with PBKDF2-derived password key. kdfSalt stored but useless without password. Bcrypt hashes protect login passwords.
Email interception of private key Key attachment is AES-256-GCM encrypted. Password required to decrypt — interceptor cannot derive the key without it.
Man-in-the-Middle (network) All traffic over HTTPS/TLS (production). JWT token expiry limits session hijack window.
Unauthorized file access Download endpoint verifies req.user.email == document.recipientId. JWT validates identity on every request.
Sender impersonation BLS signatures tied to sender's IBE private key (derived by KDC from msk + email). Forging requires knowing the master secret key.
Replay / token theft JWT has configurable expiry (JWT_EXPIRES_IN, default 1 day). Secret stored only in env vars.
Key on disk (KDC host) Raw key file deleted immediately after reading into memory. Key never persisted beyond the moment of generation.
Private key in browser memory Key held only as React state; cleared on logout/page refresh. Never written to localStorage or IndexedDB.
OTP brute force 6-digit OTP with 10-minute expiry; PendingRegistration document deleted after use or expiry.
Email domain spoofing KDC enforces @iiita.ac.in domain check at registration. IBE key is inherently tied to the verified email.
Path traversal / injection in keygen executeKeygen validates emailId against regex /^[a-zA-Z0-9@._-]+$/ before passing to execFile (uses argument array — no shell injection).

Summary of Security Properties

  • IBE ensures any valid IIITA email is an implicit public key — no PKI required.
  • BLS signatures guarantee sender authentication and file integrity.
  • AES-256-GCM with PBKDF2 (100k iterations, SHA-512) protects private keys at rest and in transit.
  • Architectural separation (two DBs, two servers) prevents any single breach from yielding both ciphertext and key.
  • All cryptographic operations execute client-side in WebAssembly — the server is a dumb ciphertext store.
  • No plaintext ever leaves the sender's browser; no decrypted data ever reaches the server.
