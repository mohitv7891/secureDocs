Section 1

Architecture Overview

Core principle: No single compromised service can expose both encrypted files and decryption keys. The KDC and data server run independently with separate MongoDB clusters. All cryptography runs client-side in WebAssembly — servers only ever see ciphertext.

Section 2

IBE Cryptography

Scheme: Boneh–Franklin IBE using bilinear pairings (Type A curve via PBC library). The user's email address is their public key — no certificate authority needed.

Setup (run once)

Outputs: master_secret_key.dat + public_params.dat
g ∈ G1  ← random generator
msk ∈ Zr  ← master secret (KDC only)
P_pub = g^msk  ← master public key

Keygen (per user)

Runs C binary on KDC for every new user
Q = H(email)  ← hash ID to G1
d = Q^msk  ← private key → AES-wrap → email

Encrypt (WASM, client)

encrypt(publicParams, recipientEmail, msg, sig)
Q = H(recipient),  r ∈ Zr random
U = g^r
g_T = e(Q, P_pub)^r  ← shared secret
V = (msg ‖ sig) ⊕ KDF(g_T)
ciphertext = U ‖ V

Decrypt (WASM, client)

decrypt(privateKey, ciphertext) → msg + sig
g_T = e(U, d)  ← same value (bilinear property)
plaintext = V ⊕ KDF(g_T)

Digital Signatures (BLS-style, identity-bound)

Sign — sender signs file before encryption
h = H_Zr(file)  ← SHA-256 → Zr element
σ = d_sender^h  ← signature in G1
Verify — recipient checks after decryption
Q_s = H(senderEmail)
e(σ, g) == e(Q_s^h, P_pub)  ← valid?
Why signatures are inside the encryption V = (file ‖ sig) ⊕ KDF(g_T) — the signature is encrypted with the file, so only the recipient can verify sender identity. Eavesdroppers see nothing.
Section 3

End-to-End Pipeline

Registration

1
User → KDC: email + password
POST /api/auth/initiate-registration — validated for @iiita.ac.in, password ≥6. Bcrypt-hash password, generate 6-digit OTP via crypto.randomInt, store PendingRegistration (TTL 10 min).
2
KDC → User: OTP email via Nodemailer
Gmail SMTP port 465, TLS. Plain-text OTP with 10-min expiry notice.
3
User → KDC: OTP verify
POST /api/auth/verify-registration — check OTP match + expiry.
4
KDC: run native C keygen binary
execFile('keygen', [email], {cwd: NATIVE_CRYPTO_DIR}) — computes d = H(email)^msk, writes {email}_private_key.dat. 5 s timeout.
5
KDC: AES-256-GCM wrap private key with user's password
16-byte random salt → PBKDF2(password, salt, 100 000 iter, SHA-512, 32 B) → AES-GCM encrypt → package: [salt(16) | authTag(16) | IV(12) | ciphertext]. Raw key file deleted immediately.
6
KDC → User: encrypted key as email attachment
Nodemailer attaches encrypted_private_key_{email}.dat. User instructed to store it safely. KDF salt saved to MongoDB (User.kdfSalt). PendingRegistration deleted.

Login & Key Load

1
User → KDC: login credentials
POST /api/auth/login — bcrypt.compare → sign JWT { user: {id, email} }, 1-day expiry, shared JWT_SECRET. Token stored in localStorage.
2
User loads .dat file + password in browser (KeyLoader component)
Web Crypto API: PBKDF2 re-derives AES key → AES-GCM decrypts blob → raw IBE private key stays in browser memory only. Never sent to any server.
3
Dashboard loads WASM module + public parameters
Fetches /crypto_module.js, /a.param, /public_params.dat from Vite static server. Mounts a.param into Emscripten MEMFS. Pairing engine initialized in browser.

File Upload (Sender)

1
WASM: sign raw file bytes
wasm_sign_buffer(senderPrivKey, fileBytes) → σ = d_sender^H_Zr(file) in G1.
2
WASM: IBE-encrypt (file ‖ signature) for recipient email
wasm_encrypt_buffer(publicParams, recipientEmail, fileBytes, sigBytes) → U ‖ V.
3
POST ciphertext to data server
POST /api/files/upload-encrypted — FormData: encryptedFile blob + recipientId. JWT in Authorization header. Multer reads into memory (max 100 MB). Saved as Document in MongoDB.

File Download & Verify (Recipient)

1
GET received file list (metadata only)
GET /api/files/received — Document.find({ recipientId: req.user.email }), excludes encryptedData field.
2
GET encrypted blob — authorization check enforced
GET /api/files/download-encrypted/:id — server checks document.recipientId === req.user.email. Returns { encryptedDataB64 }.
3
WASM: decrypt → verify signature
wasm_decrypt_buffer(privKey, ciphertext) → file + sig. Then wasm_verify_buffer(pubParams, senderEmail, file, sig) → 0 valid / 1 invalid. UI shows result. Plaintext never leaves browser.

Section 5

Interview Q&A

1
What is IBE and why did you use it instead of RSA/PGP?

IBE uses the recipient's email address as their public key — no certificate authority, no key exchange beforehand. A sender can encrypt for alice@iiita.ac.in without Alice having set up anything. In a closed institutional setting this eliminates all PKI management overhead. The math uses bilinear pairings: a sender computes a shared pairing value from the recipient's identity and the master public key; the KDC derives the matching private key from the master secret and the same identity hash.

2
Why is the KDC separate from the data server?

This is the core architectural decision. If both ran together, one breach would give an attacker both the ciphertext and the ability to generate decryption keys. By running them on separate processes with separate MongoDB clusters, neither can act alone: the data server has ciphertexts but no keys; the KDC has key-generation capability but no stored files. The only shared element is JWT_SECRET for stateless identity verification — which proves who you are, not what you can decrypt.

3
How does file encryption and decryption work end to end?

Sender: loads IBE private key from .dat file via Web Crypto, signs the raw file (σ = d^h), then IBE-encrypts (file ‖ signature) for the recipient's email — picking random r, computing ephemeral public value U = g^r and shared pairing value g_T = e(Q, P_pub)^r, XOR-streaming the plaintext with a SHA-256 counter KDF over g_T. Uploads ciphertext U ‖ V. Recipient: downloads blob, decrypts with their private key (g_T = e(U, d) gives the same value by the bilinear property), splits out file and signature, verifies signature against sender's email. All of this runs in WASM in the browser.

4
How is the IBE private key protected?

After keygen the raw key is immediately AES-256-GCM encrypted using a key derived by PBKDF2 (100 000 iterations, SHA-512) from the user's own password and a fresh 16-byte random salt. Package layout: [salt(16) | authTag(16) | IV(12) | ciphertext]. This blob is emailed as an attachment — never stored in any database. The salt alone (which is in MongoDB) is useless without the ciphertext. The ciphertext alone (in email) is useless without brute-forcing the password through 100k PBKDF2 rounds. The raw key file is deleted from disk immediately after wrapping.

5
Why WebAssembly for cryptography?

IBE requires the PBC library (pairing-based cryptography) written in C, which depends on GMP for arbitrary-precision arithmetic. There is no equivalent in JavaScript. Compiling it to WASM with Emscripten lets me run the same audited C code in the browser at near-native speed. Critically, the private key never has to leave the browser — there is no "send key to server and decrypt there" API, which would be the obvious weaker alternative.

6
What are bilinear pairings and why are they needed for IBE?

A bilinear pairing is a map e: G1 × G1 → GT with the property e(aP, bQ) = e(P, Q)^(ab). This lets the scheme work: the encryptor computes e(Q, P_pub)^r = e(Q, g)^(msk·r), and the decryptor computes e(g^r, Q^msk) = e(g, Q)^(r·msk) — identical values from different inputs. Without this algebraic property there is no way to couple a ciphertext (computed from an identity string and public params) to a private key (computed by the KDC from the master secret).

7
What does Nodemailer do and why is out-of-band key delivery important?

Nodemailer sends two emails: (1) the OTP during registration, proving the user controls the institutional address; (2) the encrypted .dat key attachment after keygen. Delivering the key via email means it is never stored on any server — an attacker who fully compromises both servers still cannot get the key. Recovery requires both the email account and the user's password, two independent factors the server never holds simultaneously.

8
How does authentication work across two separate backend services?

The KDC issues JWTs signed with JWT_SECRET (payload: { user: { id, email } }, 1-day expiry). The data server shares the same JWT_SECRET and verifies tokens independently — no call back to the KDC needed. This stateless design means the data server knows who the request is from (email, id) without storing sessions or calling a remote auth service. The data server never issues tokens; it only consumes them.

9
What happens if someone uploads a file for the wrong recipient?

It is mathematically useless to them. IBE encryption is identity-bound — the shared secret e(Q, P_pub)^r is derived specifically from the recipient's identity hash. Only a private key derived from that same identity (by the KDC using the master secret) can reproduce the shared secret via e(U, d). A wrong recipient who downloads the ciphertext cannot decrypt it with their own private key — the pairing values will not match.

10
One-sentence summary of SecureDocs for an interviewer?

SecureDocs encrypts documents end-to-end in the browser using Boneh–Franklin IBE compiled to WebAssembly — where the recipient's email is their public key — stores only opaque ciphertext on the server, and delivers IBE private keys out-of-band as AES-256-GCM wrapped email attachments, so no server at any point holds both data and keys.
